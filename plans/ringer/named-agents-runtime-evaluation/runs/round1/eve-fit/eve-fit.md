## Executive Finding

**Access date: 2026-07-26. Decision: keep Hermes-inside-Orgo as the exclusive production owner of schedules and Slack events. Do not give eve production trigger ownership yet.** Eve is a credible candidate for a later control-plane replacement, but it is explicitly beta, its safest controls require application code and configuration, and no completed Maya benchmark was supplied that demonstrates a material reduction in runtime glue or operational toil. The official repository warns that APIs and behavior may change before general availability ([Vercel eve repository](https://github.com/vercel/eve#beta-terms)).

The comparison must start with Maya. Her existing, authenticated Orgo computer plus an isolated Hermes home is the lowest-change baseline: Orgo officially describes persistent computers that run continuously and explicitly supports installing Hermes Agent for a 24/7 runtime ([Orgo API index](https://docs.orgo.ai/llms.txt)). The read-only 2026-07-26 check in the supplied evidence packet establishes the existing Maya computer and indicates that the temporary key is account-wide; it does **not** establish that Hermes, Slack, Gmail, receipts, approvals, or health reporting pass the required workload.

Therefore the baseline must first be measured on the same synthetic Maya fixture used for eve. Until eve beats that measured baseline and passes the repository's third-party-agent-tool gate, Hermes remains the sole trigger owner. A pilot may call eve only through a manual, authenticated test route with synthetic data; it must not subscribe to production Slack events or install production schedules.

## Gaps and Unknowns

- **Beta stability:** eve's own repository says framework, API, documentation, and behavior may change before GA ([official repository](https://github.com/vercel/eve#beta-terms)). Pin an exact package version and commit; do not deploy `latest` in the pilot.
- **Multi-identity Slack:** Vercel documents one channel using a named Connect credential and says Connect handles multi-workspace tenancy ([Slack docs](https://github.com/vercel/eve/blob/main/docs/channels/slack.mdx)). That is not proof that one eve project safely hosts seven distinct bot identities in the same workspace. Use seven separately deployed top-level agents/Connect clients, or prove isolation experimentally; do not multiplex persona selection through a shared token.
- **Gmail versus Resend:** Resend threaded email is documented ([Chat SDK channel docs](https://github.com/vercel/eve/blob/main/docs/channels/chat-sdk.mdx)); native Gmail mailbox semantics are not established by the reviewed official eve sources. Resend may suit a new service address but cannot silently replace the required `@cc.proexteriorsus.net` Google Workspace identities, existing mailbox history, labels, delegates, or the already-authenticated Maya session.
- **Runtime health:** Agent Runs supplies trace detail, but the documented UI does not by itself establish the required queue depth, last/next business cadence, cross-agent kill switch, spend circuit breaker, or durable receipt retention ([Vercel observability announcement](https://vercel.com/changelog/eve-agent-observability)). Those remain Command Center features.
- **Schedule approval semantics:** task-mode schedules cannot wait for a person or OAuth; handler-mode channel sessions can ([schedule docs](https://github.com/vercel/eve/blob/main/docs/schedules.mdx)). Any scheduled external action implemented in task mode is a design failure.
- **Event exactly-once behavior:** the Slack adapter exposes Slack `event_id` metadata and raw callbacks ([Slack docs](https://github.com/vercel/eve/blob/main/docs/channels/slack.mdx)), but the official material reviewed does not guarantee end-to-end exactly-once creation of `dashboard_work_items`. Persist an idempotency key such as Slack team/event ID in Supabase and enforce a unique constraint.
- **Orgo invocation:** eve can call HTTPS OpenAPI/MCP connections with injected credentials ([OpenAPI connection docs](https://github.com/vercel/eve/blob/main/docs/connections/openapi.mdx)); Orgo uses Bearer authentication and keys are account-wide or workspace-scoped ([Orgo authentication](https://docs.orgo.ai/api-reference/authentication), [Orgo API index](https://docs.orgo.ai/llms.txt)). A thin typed Orgo tool is feasible, but the exact Orgo schema, long-running computer-use loop, screenshots, timeouts, and audit receipts must be proven. Map `ORGO_PE_CC_MAYA_API_KEY` at runtime; never rename/copy its value into a prompt or sandbox.
- **Measured advantage:** no comparative Maya run results were supplied. Eve is therefore not proven to materially reduce glue, cost, or operator toil versus Hermes-on-Orgo.

## Security and Egress

Eve separates the app runtime from the sandbox: tools can use runtime secrets while the sandbox does not receive environment variables; connection tokens are injected and not durably serialized ([security model](https://github.com/vercel/eve/blob/main/docs/concepts/security-model.md)). That is a useful boundary, but the official responsible-use guidance says approval, tool restrictions, route authorization, connection scopes, sandbox controls, telemetry, retention, and deletion remain the operator's responsibility ([responsible-use guidance](https://github.com/vercel/eve/blob/main/docs/responsible-use.md)).

The critical default is unsafe for this workload: sandbox network egress is `allow-all`. Eve recommends `deny-all` or an explicit allowlist for sensitive production work; Vercel and microsandbox backends support domain-level policies and firewall credential brokering ([sandbox docs](https://github.com/vercel/eve/blob/main/docs/sandbox.mdx)). The pilot must start deny-all and permit only the selected model endpoint, Command Center API, scoped Supabase/API facade if absolutely necessary, Orgo API, and explicitly approved external research domains. Rowan must have no internal-data routes at all.

Do not place a Supabase service-role key in any persona runtime. Preserve Supabase as the source of truth behind least-privilege Command Center endpoints/RPCs, with database constraints for Slack deduplication and receipts. Eve session state, Vercel Workflow state, sandbox files, traces, and Resend state are execution data—not authoritative operational records.

Data may egress to Vercel's workflow, sandbox, observability, Connect, and AI Gateway services; the selected model provider; configured OTEL destinations; Slack; Resend if used; Orgo; and any sandbox-allowed host. Eve explicitly says operators must assess channel, provider, connected-service, sandbox-egress, telemetry, retention, and deletion choices ([security model](https://github.com/vercel/eve/blob/main/docs/concepts/security-model.md)). Before any real data, inventory fields sent to each processor, redact PII and financial attachments where possible, set retention/deletion controls, verify region/DPA/subprocessors, and prohibit raw credentials in traces or receipts.

The repository's `third-party-agent-tool gate` applies before eve, its installers, Connect, Chat SDK/Resend adapters, sandbox images, MCP servers, skills, or wrappers touch production. Required evidence includes A3 traceability, Apache-2.0/license and provenance review, egress review, installer/permission review, SkillSpector where applicable, local-MCP compliance, rollback, and human approval. Eve's open-source license is Apache-2.0 ([official license](https://github.com/vercel/eve/blob/main/LICENSE)); that satisfies only the license fact, not the full gate.

## Pilot Shape

1. **Measure Hermes first.** On Maya's existing Orgo computer, run an isolated Hermes home against synthetic Slack, synthetic Gmail, and a staging Command Center/Supabase surface. Capture the comparison metrics above. Orgo officially supports Hermes as a 24/7 runtime ([Orgo API index](https://docs.orgo.ai/llms.txt)).
2. **Gate and pin eve.** Complete the third-party review; pin the npm version and Git commit; inventory dependencies/installers; approve a data-flow diagram and egress allowlist. Eve is beta ([official repository](https://github.com/vercel/eve#beta-terms)).
3. **Deploy a shadow Maya.** Use a separate eve project, test Slack app, test Connect client, test email address, scoped staging Command Center token, and a workspace-scoped Orgo key. Reuse Maya's existing computer by immutable ID; do not provision or replace it. Do not give this project Supabase service-role access.
4. **No production triggers.** Hermes alone continues to own production Slack events and schedules. Eve is invoked only by an authenticated manual test route or one-shot harness. The same synthetic event is injected separately into each benchmark, never delivered by two live subscribers.
5. **Implement safe workflow shape.** A Slack event first inserts one uniquely keyed Command Center work item, then starts the durable workflow. External Slack/email writes are idempotent, tool-gated, and human-approved. Scheduled approval-sensitive paths use handler mode, not task mode ([schedule docs](https://github.com/vercel/eve/blob/main/docs/schedules.mdx)).
6. **Gmail proof, not substitution.** First read/classify one synthetic message via Maya's existing Orgo/Google session without exposing unrelated mail. Separately test a scoped Google API connection only if approved. Treat the documented Resend adapter as a different email option, not Gmail parity ([Chat SDK channel docs](https://github.com/vercel/eve/blob/main/docs/channels/chat-sdk.mdx)).
7. **Failure and recovery tests.** Kill/redeploy mid-tool and mid-approval; verify retry idempotency, trace/receipt linkage, deny-all egress, credential non-disclosure, spend ceiling, kill switch, and recovery. Eve documents step replay and interrupted-step rerun behavior ([durability docs](https://github.com/vercel/eve/blob/main/docs/concepts/execution-model-and-durability.md)).
8. **Promotion gate.** Promote eve only if repeated Maya trials beat Hermes on reliability and operator toil while meeting every identity, approval, receipt, security, cost, and rollback gate. Then transfer trigger ownership atomically: pause/disable Hermes Slack and cron, verify zero active deliveries, enable eve, and monitor unique event keys. Roll out serially to Alex, Casey, Jordan, Sam, Rowan, and Lena.

**Rollback:** disable the eve Slack trigger and Vercel cron routes/project, revoke its Slack/Connect, Command Center, model, Resend/Google, and workspace-scoped Orgo credentials, and re-enable the previously paused Hermes gateway/scheduler from versioned configuration. Because Command Center/Supabase and the existing Orgo desktop remain authoritative and unchanged, rollback requires no data migration, desktop replacement, or DNS change. Vercel also supports deployment rollback, but that is not the control-plane rollback and does not prevent duplicate ownership by itself ([Vercel launch post](https://vercel.com/blog/introducing-eve)).

## Recommendation

**Select Hermes-inside-Orgo as the exclusive production owner of schedules and Slack events now.** Eve should receive a bounded, synthetic Maya shadow pilot only after Hermes is measured and the third-party-agent-tool gate passes. Do not run both as production subscribers or schedulers.

Reconsider exclusive ownership only after eve demonstrates, on the same Maya fixtures, zero duplicate/missed events, complete Command Center receipts, safe restart/retry behavior, approval enforcement, Gmail/Orgo identity isolation, acceptable egress and retention, lower operator toil, bounded cost, and a timed rollback. If it wins, transfer Slack and schedule ownership atomically to eve and leave Hermes either disabled or callable only as an explicitly invoked worker. If it does not win, stabilize Hermes for Slack/API work and keep Orgo as the persistent browser runtime for all seven personas.
