# Cursor Cloud Agents/Automations and Devin Fit Assessment

## Executive Finding

**Accessed 2026-07-26.** Cursor Cloud Agents/Automations and Devin are credible **development-workforce** products and possible **browser-only adjuncts**, but neither should be the core runtime for the Open Brain's 13-agent workforce. The core runtime must preserve distinct Accounting, Operations, Sales, Marketing, Executive, Capture, Historian, Researcher, Conductor, Auditor, Quality Control, Innovator, and Maintenance identities, their security boundaries, approval rules, and durable provenance. Neither vendor documents that model.

Cursor is the better fit for the **DevTeam plane**: repo-native cloud work, event/schedule-driven maintenance, PR production, isolated development environments, and optional customer-run execution workers. Cursor Automations run on schedules or events from Slack, GitHub, Linear, PagerDuty, and webhooks, use configured MCPs, and expose memory across runs ([Cursor Automations](https://cursor.com/changelog/03-05-26)). Cloud agents test in sandboxes and produce screenshots, recordings, logs, commits, and PR-oriented output ([Cursor Cloud Agents](https://cursor.com/cloud)).

Devin is also a strong development workforce and has the more explicitly documented general desktop/browser surface, reusable Knowledge/Playbooks, scheduled sessions, session API, service-user RBAC, and enterprise audit API ([Computer Use](https://docs.devin.ai/work-with-devin/computer-use), [Playbooks](https://docs.devin.ai/product-guides/creating-playbooks), [Scheduled Sessions](https://docs.devin.ai/product-guides/scheduled-sessions), [Create Session API](https://docs.devin.ai/api-reference/v3/sessions/post-organizations-sessions), [Audit Logs API](https://docs.devin.ai/api-reference/v3/audit-logs/enterprise-audit-logs)). That makes Devin a plausible secondary DevTeam worker or tightly scoped browser adjunct, not a Roofing-Ops persona runtime.

Neither product should directly embody Roofing-Ops personas or own unsupervised operational authority. Neither vendor's official documentation reviewed here establishes native Gmail/Outlook mailbox access; Devin documents email **notifications**, not inbox operation, while Cursor documents triggers/tools but no native mailbox connector ([Scheduled Sessions](https://docs.devin.ai/product-guides/scheduled-sessions), [Cursor Automations](https://cursor.com/changelog/03-05-26)). Any email capability would therefore be an external integration requiring separate identity, scopes, egress controls, approval gates, and audit evidence.

## Cursor Findings

- **Identity and Slack:** Cursor documents a single `@Cursor` Slack app that launches agents and reports in the originating thread; it does not document multiple independently permissioned bot identities corresponding to named business personas ([Cloud Agents](https://cursor.com/cloud)). Service accounts can invoke cloud agents without binding automation to a person, but service accounts are API/admin identities, not documented Slack persona identities ([Enterprise service accounts](https://cursor.com/changelog/enterprise-dec-2025)).
- **Scheduled and event work:** Automations support schedules and Slack, Linear, GitHub, PagerDuty, and webhook events; each invocation creates a cloud sandbox and uses configured models and MCPs ([Automations](https://cursor.com/changelog/03-05-26)). Later documentation adds Slack emoji triggers, more GitHub events, and computer use for automation runs ([Automation improvements](https://cursor.com/changelog/06-18-26)).
- **Browser/computer use:** Cloud agents can control remote computers, test software, record demonstrations, and allow a human to take over the remote desktop ([Cloud Agents](https://cursor.com/cloud)). This is compelling for UI verification and narrowly scoped web tasks, but official materials frame it around building and testing software rather than durable business-process automation.
- **Secrets and isolation:** Cursor documents encrypted-at-rest development secrets, isolated AWS VMs, internet access, and automatic execution of terminal commands for cloud agents; it explicitly warns that prompt injection can cause exfiltration ([Background/Cloud Agent security](https://docs.cursor.com/background-agent)). Newer development environments add build-only secrets, per-environment secret and egress scopes, version history, rollback controls, and environment audit logs ([Development environments](https://cursor.com/changelog/05-13-26)).
- **Durable state:** Automations have a memory tool that can learn from past runs ([Automations](https://cursor.com/changelog/03-05-26)). Cursor also describes external MCP-backed persistent data for its own security automations, which shows that important structured state may need a separately governed system of record ([Security automations](https://cursor.com/blog/security-agents)). Memory is useful learning context, not a substitute for the Open Brain's curated, provenance-bearing records.
- **Approval and audit:** Cloud agents auto-run commands, unlike foreground agents' per-command approval behavior ([Background/Cloud Agent security](https://docs.cursor.com/background-agent)). Enterprise Hooks can log or block commands and tool calls, and Cursor's admin audit log tracks access/configuration events; sandbox policy is centrally configurable ([Cursor Enterprise controls](https://cursor.com/blog/enterprise)). These are good engineering controls, but the cited material does not establish per-business-action approval semantics for invoices, scheduling, customer communication, or trust-tier changes.
- **Repo workflow:** Cursor is strongly repo-centered: agents work in isolated development environments, test changes, generate review artifacts, and produce merge-ready work ([Cloud Agents](https://cursor.com/cloud)). GitHub/Slack/Linear/Jira entry points and automation triggers reinforce the DevTeam fit ([Cloud Agents](https://cursor.com/cloud)).
- **Hosting:** Cursor offers **self-hosted cloud-agent workers** so code, execution, outputs, and secrets stay on internal machines ([Self-hosted Cloud Agents](https://cursor.com/changelog/03-25-26)). This is not full on-prem Cursor: Cursor separately states that it does not offer an on-premises product deployment and that AI requests route through Cursor's backend for prompt construction ([Cursor Enterprise](https://cursor.com/en-US/enterprise), [Privacy & Security](https://docs.cursor.com/account/privacy)).

## Devin Findings

- **Identity and Slack:** Devin installs one Slack app, is invoked as `@Devin`, links each human through matching email, and replies in-thread ([Slack integration](https://docs.devin.ai/integrations/slack)). A workspace admin may rename the bot username/avatar, but the documentation does not describe multiple simultaneous, separately authorized named bot identities ([Slack integration](https://docs.devin.ai/integrations/slack)). Therefore renaming `@Devin` cannot safely implement the 13-agent roster.
- **Scheduled and event work:** Scheduled Sessions support recurring cron-style or one-time runs, optional Playbooks, repositories, run-as attribution, email notifications, and Slack-channel notifications; past one-time sessions remain for audit ([Scheduled Sessions](https://docs.devin.ai/product-guides/scheduled-sessions)). Devin's API release notes document schedules in the v3 API and session origins including Slack, API, and automation ([API release notes](https://docs.devin.ai/api-reference/release-notes)).
- **Email:** Official documentation reviewed here supports emails about scheduled-run results, not reading, searching, composing, or sending through a user's mailbox ([Scheduled Sessions](https://docs.devin.ai/product-guides/scheduled-sessions)). No native Gmail or Outlook connector is listed in Devin's official integration overview; external systems are connected through MCP or credentials ([Integrations Overview](https://docs.devin.ai/integrations/overview)).
- **Browser/computer use:** Devin has a full Linux desktop, native browser/computer tools, recordings, and a Chrome DevTools endpoint for Playwright; browser cookies, local storage, and authentication state persist within its browser context ([Computer Use](https://docs.devin.ai/work-with-devin/computer-use)). This is the clearest case for a restricted browser-only adjunct.
- **Secrets:** Devin supports organization-level secrets under service-user RBAC and identifies sensitive values and cookie secret types ([Secrets API](https://docs.devin.ai/api-reference/v3/secrets/organizations-secrets)). Enterprise environment guidance supports enterprise, organization, and repository secret scopes and warns never to put secrets in YAML because they can enter logs and artifacts ([Environment best practices](https://docs.devin.ai/enterprise/environment-management/best-practices)).
- **Durable state:** Knowledge provides reusable cross-session guidance and Playbooks provide reusable, versioned procedures; Playbooks can be reverted ([Playbooks](https://docs.devin.ai/product-guides/creating-playbooks)). These are useful development instructions, not an authoritative operational ledger. The session API exposes parent/child sessions, origin, status, tags/metadata, and structured output, making external state capture feasible ([Create Session API](https://docs.devin.ai/api-reference/v3/sessions/post-organizations-sessions)).
- **Approval and audit:** Interactive Planning can require explicit approval before coding, although the default documented behavior is to continue after 30 seconds unless configured otherwise ([Interactive Planning](https://docs.devin.ai/work-with-devin/interactive-planning)). The session API exposes `bypass_approval` and a `waiting_for_approval` safe-mode state, so policy must prohibit bypass for sensitive work ([Create Session API](https://docs.devin.ai/api-reference/v3/sessions/post-organizations-sessions)). Enterprise audit logs identify action, time, organization, service user, and human user and are retrievable through a permissioned API ([Audit Logs API](https://docs.devin.ai/api-reference/v3/audit-logs/enterprise-audit-logs)).
- **Repo workflow:** Devin natively integrates with GitHub, GitLab, Bitbucket, and Azure DevOps for repository access and pull/merge requests and supports Jira and Linear initiation ([Integrations Overview](https://docs.devin.ai/integrations/overview)). Its workspace includes shell, browser, and editor, with one isolated machine per session in Enterprise Cloud ([Enterprise Deployment](https://docs.devin.ai/enterprise/deployment/overview)).
- **Hosting:** Devin is not fully self-hostable. Its Brain always resides in Cognition Cloud. Enterprise Cloud hosts Brain and Devbox there; Customer Dedicated Deployment places managed Devboxes in a customer-isolated single-tenant VPC connected by PrivateLink or IPSec, while the Brain remains in Cognition Cloud ([Enterprise Deployment](https://docs.devin.ai/enterprise/deployment/overview)).

## Security and Identity

The core architectural mismatch is **principal identity**. A Slack display name is not an authorization boundary. Cursor's single `@Cursor` app and Devin's single renameable `@Devin` app do not document separate app installations, credentials, scopes, policies, memory stores, or audit principals for each Open Brain persona ([Cursor Cloud Agents](https://cursor.com/cloud), [Devin Slack](https://docs.devin.ai/integrations/slack)). Roofing-Ops messages must continue to originate from the existing persona runtime, which can delegate a bounded technical/browser job and then attribute the returned evidence to the correct persona.

For the **DevTeam plane**, provision a non-human service principal, restrict it to designated repositories and environments, and preserve the triggering human and originating ticket/thread in every run. Cursor documents service accounts and centralized repository/MCP controls ([Service accounts](https://cursor.com/changelog/enterprise-dec-2025), [Cursor Enterprise](https://cursor.com/en-US/enterprise)); Devin documents service-user credentials, RBAC permissions, and user impersonation constraints ([Create Session API](https://docs.devin.ai/api-reference/v3/sessions/post-organizations-sessions)). Do not use impersonation or Slack renaming to simulate Roofing-Ops personas.

Browser work carries prompt-injection and exfiltration risk. Cursor explicitly says cloud agents have internet access, auto-run terminal commands, and can be induced to upload code ([Cloud Agent security](https://docs.cursor.com/background-agent)). Devin's persistent browser authentication state makes secrets useful but also increases the consequence of a compromised session ([Computer Use](https://docs.devin.ai/work-with-devin/computer-use)). Browser adjuncts should therefore receive task-specific accounts, destination allowlists, no general customer mailbox, no production-wide credential, short-lived sessions, and mandatory evidence/approval before consequential writes.

## Best-Fit Roles

## DevTeam plane

- **Cursor — preferred development workforce:** issue-to-PR work, test creation, CI repair, dependency maintenance, security/code review automations, UI verification, and review artifacts. Keep branch protection and human merge/deploy gates external to Cursor.
- **Devin — secondary development workforce:** complex repository tasks where its explicit Knowledge/Playbook model, session API, planning approval, or broad desktop/browser environment provides material advantage. Avoid duplicating always-on automations across both vendors without a single owner and deduplication key.
- **Either — browser-only adjunct:** UI regression checks and narrow, reversible web actions using least-privilege accounts. Devin is preferred when general browser/desktop interaction is central; Cursor is preferred when the browser is used to verify code the agent just changed.

## Roofing-Ops personas

- **Neither as core runtime or direct persona.** Accounting/Ops/Sales/Marketing/Executive must remain identities in the Open Brain, not aliases of a vendor bot.
- A persona may delegate a bounded job such as “capture screenshots of a permit portal” or “reproduce this Command Center UI defect.” The persona runtime must supply the task, enforce authorization, ingest evidence, and make or request the consequential decision.
- Do not assign either product autonomous invoicing, payment, customer email, crew scheduling, permit submission, trust-tier edits, internal/external retrieval routing, or publication authority based solely on its vendor approval UI.

## Recommendation

1. **Do not replace the Open Brain core runtime with Cursor or Devin.** Preserve its named Slack principals, Historian/Researcher boundary, Auditor/Quality-Control separation, approval semantics, and provenance store.
2. **Pilot Cursor as the primary DevTeam workforce** on one low-risk repository and two workflows: issue-to-PR and scheduled CI/security maintenance. Require isolated environments, environment-scoped secrets and egress, service-account attribution, branch protection, test evidence, and human merge/deploy approval ([Development environments](https://cursor.com/changelog/05-13-26), [Service accounts](https://cursor.com/changelog/enterprise-dec-2025)).
3. **Evaluate Devin only where it is differentiated:** a complex repo task using Knowledge/Playbooks or a narrow browser workflow needing Linux desktop/Playwright control. Use explicit plan approval, prohibit `bypass_approval`, export session/audit records, and grant task-specific credentials ([Interactive Planning](https://docs.devin.ai/work-with-devin/interactive-planning), [Create Session API](https://docs.devin.ai/api-reference/v3/sessions/post-organizations-sessions), [Computer Use](https://docs.devin.ai/work-with-devin/computer-use)).
4. **Keep email out of both pilots.** Neither reviewed official product surface establishes native mailbox operation. If later needed, integrate a separately governed mailbox connector behind the Open Brain's persona authorization and human-approval layer.
5. **Classify the outcome:** Cursor = **development workforce (recommended)** and code-verification browser adjunct; Devin = **optional development workforce** and **browser-only adjunct**; both = **not core runtime** and **not Roofing-Ops persona hosts**.
