# Review Report

## Summary

The implemented PEC-78 Maya Composio production path passes this read-only security review. The reviewed path verifies the Composio delivery before parsing, encrypts minimized Slack content before storage, authorizes runtime operations with DPoP and database-enforced identity/fence/capability/gate bindings, binds the only Slack effect to the claimed event and thread, confines provider credentials, treats message content as prompt-injection-capable untrusted data, and stops on unknown provider outcomes. The worker has no Slack token or direct Slack SDK path: its only production Slack effect is the pinned Composio `SLACKBOT_SEND_MESSAGE` tool version `20260721_00`.

Activation remains a separate human-controlled operation. The migration seeds the receive grant and ingress source disabled, the Supervisor program has `autostart=false` and zero start retries, and the installer proves the exact program is stopped. The trigger-first rollback disables and confirms the exact Composio trigger before stopping/quarantining the worker credentials and disabling inference. Two P2 evidence/operability hardening items remain, but neither enables ingress-to-effect execution without the independently enforced runtime authority tuple and neither is a P0/P1 blocker.

Focused verification passed: Command Center PEC-78 Vitest reported 5 files and 42 tests passed; the isolated Command Center Astro production build completed; listener Node tests reported 64 passed and 0 failed.

## Findings

### F-01 — Production readiness evidence is assembled from independent predicates rather than one joined tuple

- **Evidence:** `schemas/cleverwork-roofer/190-pec78-composio-slack-production.sql:467-480` reports principal, source, receive grant, send grant, validation authorization, lease, effect, and queue predicates independently. `app/command-center/src/lib/pec78/readiness.server.ts:21-50` combines those observations with server configuration checks but does not prove them as one joined credential/principal/source/gate/grant/destination/budget/authorization tuple or compare the authorization's stored build, registry, and runtime values. Runtime authorization itself remains joined and fail-closed: token/claim/effect RPCs validate the credential, runtime instance, principal, fence, production gate, time-bounded grants, source, destination, budget, leases, and kill switches before decryption or provider I/O (`189-pec78-maya-shadow-boundary.sql`; `190-pec78-composio-slack-production.sql:287-402`).
- **Impact:** An operator could receive an incomplete or misleading pre-activation readiness snapshot assembled from individually valid rows and would need the separate deployment/worker/trigger identity evidence required by the activation checklist. This does not authorize a claim or Slack effect because the operation RPCs rejoin and revalidate the exact authority and event tuple transactionally.
- **Fix:** Replace the independent readiness predicates with one exact joined readiness query bound to the credential, runtime instance, principal, source, receive/send grants, destination, budget, gate, validation authorization, build, and registry. Return only digests and boolean/result codes, and add one negative test per mismatched join.
- **Priority:** P2
- **Confidence:** High

### F-02 — Automated rollback covers external containment but database fencing remains a documented operator step

- **Evidence:** The required rollback sequence is documented in `PEC78-MAYA-COMPOSIO-PRODUCTION.md:101-119`: disable and confirm the trigger first, stop the exact worker, fence the principal, revoke gate/capability/source, and reconcile reserved or unknown effects. `deployment/remote/orgo/maya-slack-listener/operator-rollback.mjs:32-53,132-165` automates and verifies the first-line external containment steps—exact trigger disable, exact Supervisor stop, owner-only credential quarantine, and inference-key disable—but does not invoke a database rollback RPC. Migration 190 exposes no dedicated rollback RPC. The implementation is nevertheless installed disabled, and after trigger disable plus runtime credential quarantine there is no remaining autonomous caller able to obtain DPoP tokens, claim events, or invoke Composio.
- **Impact:** Rollback is safe for immediate containment but is not a single-command, end-to-end database-plane procedure. Operators must complete and evidence the documented database fencing and manual reconciliation steps separately, increasing recovery time and the chance of incomplete administrative cleanup. It does not leave an autonomous production effect path after confirmed trigger and worker containment.
- **Fix:** Add a narrow transactional rollback RPC that fences Maya and revokes the source, grants, gate, credential, and active leases while preserving evidence and surfacing reserved/executing/unknown effects for manual reconciliation. Call it after confirmed trigger disable and worker stop, then verify a digest-only rollback receipt/readback.
- **Priority:** P2
- **Confidence:** High

## Clean

- Exact webhook authentication is correct. The route reads the body once, and the verifier computes HMAC-SHA256 over `webhook-id.webhook-timestamp.rawBody` with the configured subscription secret, decodes the Base64 V1 signature, compares equal-length bytes with `timingSafeEqual`, and rejects timestamps more than 300 seconds in either direction. Tests cover valid, malformed, missing, stale, future, and byte-mutated deliveries.
- The reviewed V3 source tuple is pinned. The webhook checks event type, trigger slug and instance ID, connected account, Composio user, Slack team, channel, owner, human-message shape, bot/self/subtype exclusions, attachment exclusions, timestamp format, and address-at-start. The per-subscription HMAC secret cryptographically binds the configured Composio project/subscription; the worker independently pins trigger UUID, account, trigger name, user, channel, team, owner, and bot identity.
- Accepted content is minimized and encrypted with AES-256-GCM using a 32-byte server-only key, a random 96-bit nonce, a 128-bit tag, versioned authenticated data, and authenticated decryption. Private tables use forced RLS, direct public/anonymous/authenticated privileges are revoked, and only service-role RPC execution is granted.
- No message text, prompt, reply, provider credential, raw webhook envelope, Slack token, or signing/encryption key is written to scoped logs or receipts. Provider IDs in operational state are opaque event/message handles; logs and local receipts use hashes, trace IDs, fixed result codes, and bounded error classes.
- DPoP verifies separate issuer and Maya Ed25519 keys; issuer, audience, subject, persona, runtime owner, contract, capability, credential, runtime instance, `cnf.jkt`, method, canonical HTTPS URL, body hash, access-token hash, issuance/freshness/expiry, and replay JTIs. Database authorization revalidates the live credential, gate, grants, fence, kill switches, and destination.
- Event and effect binding is fail-closed. Claim creates a short lease bound to credential/runtime/fence/epoch. Slack reservation requires the same event, lease, channel digest, thread digest, payload digest, destination grant, model route, budget, and idempotency key. Provider execution is a separate state transition before I/O.
- Prompt-injection handling is present at both input and output boundaries. Hermes receives a JSON-labelled untrusted message, explicit instructions not to follow embedded instructions or reveal secrets, no tool surface, a fixed model/provider, a 60-second timeout, and a 4,000-byte output bound. Output is capped, Slack references are removed, disclosure language and unverified action claims are rejected, and the fixed Maya prefix is enforced.
- The production worker contains no Slack SDK, Slack token, webhook-send, or direct Slack authorization path. It sends only through Composio using the immutable connected account/user and `SLACKBOT_SEND_MESSAGE` version `20260721_00`, with the channel/thread taken from the claimed encrypted event.
- Unknown outcomes stop safely. A prepared/executing provider ambiguity is reconciled to `failed_unknown` when possible, the event is quarantined, the worker stops, and lease reclamation excludes events with reserved, executing, or unknown effects. Interrupted provider outcomes are not automatically retried.
- Secrets are confined. Command Center webhook and encryption secrets remain server-only. The Orgo environment file must be owner-only mode 0600; startup reconstructs a minimal environment; Hermes receives only the inference credential; release/config trust chains are root-owned and hash-verified; and the Command Center never receives the Composio API key or Maya private DPoP key.
- Activation separation and rollback are credible. No active production authority or trigger is seeded, ingress defaults disabled, the worker installs stopped, and activation requires a later owner authorization and identity/hash comparison. Rollback is trigger-first, verifies the trigger disabled and exact worker stopped, quarantines its credential source, disables inference, and preserves evidence.
- Every requested first-party source file under `deployment/remote/orgo/maya-slack-listener` was inspected, including installation, trust-chain, lifecycle, rollback, legacy quarantine, runtime, Hermes, receipt, configuration, dependency-lock, and test files. Migrations 188-190, the full `app/command-center/src/lib/pec78` tree, webhook/runtime routes, middleware, and environment contract were also inspected.
