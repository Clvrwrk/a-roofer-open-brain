# Review Report

## Summary

The PEC-78 PostgreSQL/Supabase implementation is installed-disabled and contains several strong database primitives, but it is not safe to activate. Migration 190 can reclaim an event after its provider effect has already succeeded, creating an unrecoverable replay path after a crash between effect reconciliation and event completion. It also permits the `reserved -> executing` transition after credential, gate, capability, source, destination, or kill authority has been revoked. Ingress activation and readiness omit material authorization bindings, and no executable non-production PostgreSQL migration/concurrency/grant suite proves the SQL contract.

These are production-boundary failures, not documentation nits. Four P1 findings remain, so the required verdict is FAIL and migration 190 must not be promoted or activated until a forward-fix is tested on a disposable Supabase-compatible target.

## Findings

### F1 — A succeeded provider effect can be reclaimed under a new lease and cannot be completed

- **Evidence:** Lease cleanup refuses to expire an active lease only when an event-linked effect is `reserved`, `executing`, or `failed_unknown` (`schemas/cleverwork-roofer/190-pec78-composio-slack-production.sql:308-312`). It does not protect `succeeded`. Reconciliation commits the effect as `succeeded` separately (`:406-433`), and event completion is a later RPC/transaction (`:435-465`). If the worker or network fails after reconciliation commits but before completion commits, the next claim expires the lease, changes the still-`leased` event back to `received`, increments its attempt/lease epoch, and returns it under a new lease (`:308-325`). Reservation returns the old succeeded effect as a successful replay (`:367-370`); the route returns that terminal state as a normal reservation (`app/command-center/src/pages/api/agent/runtime/v1/[...path].ts:112-129`), and the worker unconditionally attempts `executing` (`deployment/remote/orgo/maya-slack-listener/production-worker.mjs:39-44`). The executing RPC then denies because the effect is no longer `reserved`, while completion under the new lease cannot succeed because the effect remains bound to the old lease/epoch.
- **Impact:** A normal crash window re-delivers plaintext and repeats inference for an already-sent message, then stops the worker with the event/effect pair stranded across different lease epochs. The current code prevents a second provider call at `executing`, but it does not provide the required idempotent recovery/completion path and leaves successful work permanently nonterminal at the event layer.
- **Fix:** Make any existing event effect block automatic reclaim unless it is explicitly safe and unsent. Atomically finalize the event with successful reconciliation, or add a recovery transition that recognizes `succeeded`, completes the event without provider I/O, and records a linked receipt. The reserve API must treat terminal existing effects as terminal and never return provider-I/O authorization. Add a two-session crash test for reconcile-committed/complete-missing and prove zero second send authorization.
- **Priority:** P1
- **Confidence:** High

### F2 — The provider-I/O transition does not recheck current authority

- **Evidence:** Reservation checks an active credential/principal, live lease/fence, production gate, send capability, source, destination, and budget (`190:339-378`). The later `pec78_mark_composio_slack_effect_executing` RPC is the transition whose receipt says `provider_io_authorized`, but it checks only stored effect/lease/credential identity, runtime instance, epoch/fence equality, lease state, and lease expiry (`:382-403`). It does not check credential state/time, principal state, production gate, send capability validity, source mode/expiry, destination state/expiry, or global/principal/credential/capability/destination/effect kill switches. Fence equality alone is insufficient because those authorities can be revoked without incrementing the principal fence. The reconcile and complete functions likewise omit most current authority checks (`:406-465`), although reconciliation should remain available through a separately scoped no-send recovery authority after a kill.
- **Impact:** A reservation made immediately before a gate/capability/source/destination/credential revocation or kill can still cross into provider I/O afterward. This defeats trigger-first rollback and the requirement that the final execution transition be fenced by current database authority.
- **Fix:** In the executing RPC, lock and revalidate the complete current authority tuple in the same transaction immediately before returning provider-I/O authorization: credential and time window, principal and fence, gate, send capability, source, destination, lease/epoch, effect expiry, and every applicable kill scope including destination/effect. Keep reconciliation available after revocation through a distinct, least-privilege reconciliation contract that cannot authorize a send. Add revoke/expire/kill races between reserve and execute for every authority type.
- **Priority:** P1
- **Confidence:** High

### F3 — Ingress consumption is not bound to the full activation authority, and enabled ingress bypasses receive capability/gate checks

- **Evidence:** `activation_authorizations` stores `build_version`, `registry_version`, `runtime_instance_id`, and `fence_epoch` (`190:35-53`), but validation-mode ingestion matches only principal/source, state, trigger, channel, fence, and time (`:263-270`). It never compares the authorization's build, registry, or runtime instance to an authoritative deployed/runtime value. More broadly, ingestion checks source tuple/mode, active principal, and global/principal/receive-capability kill switches (`:245-259`), but never requires an active `slack.receive.christopher` capability grant or production gate. In `enabled` mode it requires no activation authorization at all (`:252-271`). Consumption is transactionally row-locked and rolls back with a failed insert; source-row locking plus the two unique indexes makes the delivery/message dedupe race conservative (`:245,260-281`), but those sound concurrency primitives do not supply the missing authority.
- **Impact:** A stale or mismatched one-message authorization can be consumed by a different build/runtime/registry, and production ingress can accept and persist ciphertext while the receive capability or production gate is disabled. That breaks the claimed one-use activation boundary and makes gate/capability revocation incomplete.
- **Fix:** Make the activation handle a single-use, database-consumed capability bound to the exact build, registry, runtime instance, source tuple, principal fence, and approved fresh message window. Require an active receive grant and production gate for both validation and enabled ingestion, or document and implement a separate narrowly scoped ingress gate. Pass only server-observed binding values and compare them under the same row locks. Add stale-build, stale-registry, wrong-runtime, revoked-capability, expired-gate, and concurrent one-use tests.
- **Priority:** P1
- **Confidence:** High

### F4 — Readiness can report server-ready without critical authority, and the database contract lacks required non-production proof

- **Evidence:** The database readiness RPC hard-codes `ok: true` and reports source/capabilities/authorization plus queue counts, but omits active credential/runtime binding, production gate, destination grant, principal fence match, kill switches, activation build/registry/runtime/fence binding, migration identity, and receipt-chain health (`190:467-480`). The server readiness layer can therefore return `server_ready` when those missing controls are absent; its configured/observed lists contain the same omissions (`app/command-center/src/lib/pec78/readiness.server.ts:21-50`). The focused Vitest run passed 42 tests in five PEC-78 files, but repository search found no test that applies migrations 188-190 to PostgreSQL or asserts catalogs, role grants, forced RLS, definer ownership/search paths, ciphertext rejection, two-key duplicate races, activation consumption, two-session claims, lease expiry/reclaim, transition kill races, receipt mutation/chain behavior, or rollback. The production plan explicitly requires non-production migration proof and production preflight/backup proof before activation (`plans/ringer/named-agents-runtime-evaluation/PEC78-MAYA-COMPOSIO-PRODUCTION.md:98,121-126`), and the Supabase operating guide requires a branch/local/restored staging run before production (`docs/36-supabase-infrastructure-ops.md:159-181`).
- **Impact:** Operators can receive a false-green readiness result, while SQL signature/grant and concurrency behavior remain statically inferred rather than executed against PostgreSQL/Supabase. The application tests cannot detect migration parse/signature errors or transaction races.
- **Fix:** Derive top-level readiness from all required booleans and return false/degraded unless credential, gate, receive/send grants, destination, exact activation bindings, no applicable kill, expected migration/build/registry, empty pre-activation queue, no live lease, and no unknown effect are proven. Add a disposable PostgreSQL/Supabase integration suite with catalog/grant/RLS assertions and real two-session race tests. Run `scripts/supabase-preflight.mjs --target branch`, apply 188-190 from a production-shaped baseline, run advisors and focused app smoke tests, and retain the results. Only after a reviewed forward-fix and green branch proof should a production preflight with fresh backup proof be considered.
- **Priority:** P1
- **Confidence:** High

### F5 — Migration 190 has no complete rollback/forward-fix control for its new state

- **Evidence:** The inherited `pec78_rollback_shadow` RPC revokes the principal, credentials, grants, destinations, gates, shadow budget/schedule/leases, and generic `effects` (`schemas/cleverwork-roofer/189-pec78-maya-shadow-boundary.sql:246-293`). Migration 190 does not replace it or add an operator RPC that disables `ingress_sources`, revokes `activation_authorizations`, fences `event_leases`, and preserves/marks `slack_effects` for reconciliation. The production plan requires trigger-first disable, fence/kill, source/capability/gate revocation, and reconciliation/retention (`PEC78-MAYA-COMPOSIO-PRODUCTION.md:101-115`).
- **Impact:** The database rollback does not atomically represent the new production state machine. Although disabling the principal blocks some operations, active source/authorization rows and new leases/effects remain misleading, and there is no tested forward-fix path for a partially promoted migration or an ambiguous send.
- **Fix:** Add a forward migration with a narrowly granted operator rollback RPC that disables the ingress source and authorizations, increments the principal fence, fences active event leases, revokes send/receive authority, and retains `reserved`/`executing`/`failed_unknown` effects as reconciliation-required rather than erasing ambiguity. Test rollback from every state and test roll-forward recovery; do not attempt a destructive down migration.
- **Priority:** P2
- **Confidence:** High

## Clean

- Migration 190 replaces the capability CHECK using `NOT VALID` followed by validation, preserving existing rows while adding only `slack.receive.christopher` (`190:5-12`). The referenced inherited constraint name matches PostgreSQL's default name from migration 188.
- New migration-190 tables enable and force RLS and explicitly revoke all direct table privileges from `public`, `anon`, `authenticated`, and `service_role` (`190:144-150`). The private `runtime_auth` schema was already revoked from public API roles in migration 188 (`188:5-6`). No policies expose rows.
- All reviewed `SECURITY DEFINER` functions set explicit search paths composed of `pg_catalog` and the controlled `runtime_auth`/`extensions` schemas; migration 190 removes writable `public` from the replaced request authorizer. Public API roles are revoked and only exact public RPC signatures are granted to `service_role` (`190:482-496`). Static parameter counting found the revoke/grant signatures consistent with their declarations.
- Ciphertext rows require AES-256-GCM, a constrained key-version token, a 12-byte decoded nonce, a 16-byte decoded tag, non-empty bounded decoded ciphertext, and SHA-256-shaped binding digests (`190:57-79`). The webhook encrypts before invoking the store RPC and logs only codes/event digests (`app/command-center/src/pages/api/integrations/composio/v1/webhook.ts:19-62`).
- Ingestion serializes on the single source row, then checks both unique keys before insert and catches unique violations (`190:245-281`). Validation authorization is locked and consumed in the same transaction as insert, so an insert failure rolls consumption back.
- Claim uses database time, principal-row serialization, `FOR UPDATE SKIP LOCKED`, monotonic event lease epochs, and a partial unique active-lease index (`190:82-96,287-325`). Unknown effects correctly block automatic lease expiry/reclaim (`:308-312`).
- Effects have relational event/lease/principal/credential/destination linkage and immutable channel/thread digests (`190:98-122`). Event receipts link event, lease, effect, credential and epochs; the append function serializes the hash chain with an advisory transaction lock, and the inherited trigger rejects update/delete (`:124-183`).
- Executed evidence: `npx vitest run --configLoader runner src/lib/pec78` passed 5 files and 42 tests. `node --test test/core.test.mjs test/supervisor.test.mjs test/cc-client.test.mjs` passed 34 Orgo worker tests. Neither suite applies the migrations to PostgreSQL or exercises concurrent SQL sessions.

## Assumptions

- This was a read-only source review. No production Supabase connection, migration, DML, provider call, or deployment was performed. Production catalog state and migration history were not asserted.
- PostgreSQL behavior is assessed for the stated migration order 188 -> 189 -> 190 on a production-shaped baseline with `pgcrypto` available in `extensions`. A clean-database apply was not possible within the requested no-production/read-only boundary and no disposable database fixture was supplied.
- `service_role` is the Command Center's server-only RPC caller. Direct table DML is intentionally unavailable for the migration-190 tables; the review does not treat service-role possession itself as runtime identity.
- Reconciliation after a kill must remain possible, but through a recovery-only authority that cannot transition an effect into provider I/O. Therefore missing kill checks on reconciliation are not by themselves classified as a send vulnerability; missing checks on `mark ... executing` are.
- P1 is production-blocking under the repository governance. PASS is forbidden while any P0/P1 remains.

MACHINE_VERDICT: FAIL
