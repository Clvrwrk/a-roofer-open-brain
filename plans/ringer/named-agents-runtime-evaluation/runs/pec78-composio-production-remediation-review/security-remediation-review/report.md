# Review Report

## Summary

The PEC-78 Maya Composio production candidate passes this read-only security remediation review. Migration 191 closes the prior production blockers: the unsafe v1 ingest and no-argument readiness RPCs lose `service_role` execution; validation ingress is bound transactionally to the exact active build, registry, runtime credential, source, production gate, receive grant, fence, time window, and one-use activation authorization; the final `reserved -> executing` transition revalidates current authority and every applicable kill scope; a second execute is explicitly ambiguous and cannot authorize provider I/O; and reconciliation atomically terminalizes the effect, event, and lease.

The application and worker preserve the remaining boundaries: DPoP binds separate issuer/proof keys, tokens, method, canonical URL, body, capability, credential, and runtime; accepted Slack content is minimized and AES-256-GCM encrypted before storage; Hermes receives untrusted content as isolated data in a zero-tool, bounded environment; the only Slack send is the pinned Composio tool/account/user/destination/thread tuple; and secrets remain confined to server-only or owner-only runtime locations. Rollback disables and confirms the exact new trigger first, then invokes the database fence before runtime and inference containment, retaining ambiguous effects for reconciliation.

Local verification passed without external effects: Command Center PEC-78 Vitest reported 5 files and 45 tests passed; the isolated Astro production build completed; and listener Node tests reported 65 passed and 0 failed. Retained database evidence for preview project `zmkddrpracgxuuxiyipi` was treated only as non-production proof. This report does not attest that production migrations, deployed code, environment, source tuple, worker archive, or provider trigger state match the candidate; activation remains subject to the plan's separate live gate.

## Clean

- Migration 191 explicitly revokes `service_role` from `pec78_ingest_composio_slack_event(...)` and `pec78_composio_production_readiness()`, grants only the v2 ingest and parameter-bound readiness signatures, and the application store calls only v2.
- The v2 ingest locks the unique source, active principal, unique active runtime credential, receive grant, exact migration-191 production gate, and validation authorization. It compares build, registry, runtime instance, trigger, connected account, Composio user, Slack team/channel/owner, fence, mode, and time before consuming the one-event authorization and inserting ciphertext.
- Independent delivery and Slack-message uniqueness constraints fence duplicate deliveries and rewrapped duplicate messages. A failed ciphertext insert rolls back authorization consumption; the retained non-production suite covers that behavior and concurrent single-use ingestion/claiming.
- Claiming uses database row locks, `SKIP LOCKED`, a partial unique active-lease index, a monotonic lease epoch, a 180-second database-time lease, a two-attempt ceiling, and no reclaim when any event effect exists. Terminal effects/events therefore cannot be reclaimed.
- The migration-191 executing RPC is the sole database transition that returns `provider_io_authorized: true`. Immediately before doing so it locks and verifies the live credential/runtime, principal/fence, migration/build/registry gate, source, send grant, destination, budget, event/effect/lease binding and expiry, plus global, contract, principal, credential, capability, destination, and effect kill scopes. Schedule scope is inapplicable because this path has no schedule.
- An effect already in `executing` returns `effect_execution_ambiguous` with provider I/O unauthorized. The runtime route maps this to conflict and independently rejects replay or any response lacking the explicit provider-I/O authorization bit. The worker sends only after that unique response.
- Reconciliation updates the effect outcome, event terminal state, and lease terminal state and appends linked receipts in one database transaction. Successful reconciliation leaves no crash gap in which a succeeded effect can be reclaimed; unknown outcomes atomically quarantine and require manual reconciliation.
- DPoP uses Ed25519 with cryptographically separated issuer and Maya proof keys. Verification covers key thumbprint and `cnf`, issuer/audience/subject/persona/runtime owner/contract/capability/credential/runtime, access/proof JTIs, access-token hash, method, exact HTTPS URL, body digest, and short freshness/expiry windows; database replay claims make the proof/request path single-use.
- Webhook verification authenticates the exact raw body with HMAC-SHA256, constant-time comparison, strict header/body bounds, and a five-minute window before parsing. It rejects wrong source identities, bots/self, subtypes, attachments, malformed timestamps, unapproved authors, incidental/confusable addressing, and non-reviewed message shapes.
- Accepted content is minimized and encrypted with AES-256-GCM using a random 96-bit nonce, 128-bit tag, a 32-byte server-only key, versioned authenticated data, and authenticated decryption after a successful claim. Forced RLS and revoked direct DML protect event and receipt tables; logs use codes, trace IDs, and digests rather than message text or secrets.
- Hermes is pinned to `google/gemini-3.1-flash-lite`, one-shot, time/size bounded, tool-free, and supplied only the inference credential in its child environment. The prompt labels Slack content untrusted and denies embedded instructions, secret disclosure, tool/action claims, and identity changes; output filtering removes Slack references and rejects disclosure/action language.
- `production-worker.mjs` contains no Slack token, Slack SDK, webhook-send, or alternate provider path. It invokes only Composio `SLACKBOT_SEND_MESSAGE` version `20260721_00`, for user `maya-chen`, connected account `ca_X9dQyRDSS0sa`, channel `C0BD7L43PC2`, and the claimed source thread, with broadcasts and unfurls disabled.
- Command Center secrets are server-only. The Orgo launcher requires an owner-only 0600 environment file, rebuilds a minimal environment, verifies root-owned release/Hermes trust chains, and passes Hermes only OpenRouter authority; the Composio API key and Maya private DPoP key never enter Command Center.
- Rollback is trigger-first and fail-closed: failure to confirm the exact reviewed new trigger disabled prevents downstream mutation. After confirmation it calls the migration-191 database rollback RPC, which installs the principal kill, revokes source/authorization/gate/grants/destination/budget/credentials, fences leases, increments the principal fence, quarantines pending events, preserves reserved/executing/unknown effects, and reports reconciliation required before runtime credential quarantine and inference-key disable.
- Middleware exposes only the exact HMAC webhook path publicly and keeps the PEC-78 runtime on a separate fail-closed authorization plane. Disabled mode permits only digest-token-protected readiness and rollback endpoints, not production operations or lookalike paths.
- Focused verification results: app tests 45/45 passed; listener tests 65/65 passed; isolated Command Center production build passed. No live Supabase, Composio, Slack, Orgo, OpenRouter, Supervisor, or deployment mutation was performed.
