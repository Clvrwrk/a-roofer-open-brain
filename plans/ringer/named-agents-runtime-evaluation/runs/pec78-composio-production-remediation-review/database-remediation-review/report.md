# Review Report

## Summary

Migration 191 successfully parses and applies after migrations 188-190 in the retained non-production Supabase preview proof for project ref `zmkddrpracgxuuxiyipi`. That proof materially closes most of the prior database FAIL: it verifies forced RLS and absence of direct `service_role` DML, fences the v1 ingest and readiness RPCs, rolls back one-use authorization consumption when ciphertext constraints reject an insert, serializes single-use ingestion and event claims, exercises the ingress authority tuple, denies execute after each credential/principal/gate/source/capability/destination/budget revocation and every applicable kill scope, denies a second execute, atomically reconciles the effect/event/lease and receipts, prevents terminal reclaim, rejects receipt mutation, and fences rollback while retaining effect rows for reconciliation.

No P0/P1 database blocker remains. Two P2 hardening items are worth carrying forward: provider execution/reconciliation and rollback do not share one documented lock order, so a concurrent operator rollback can receive a visible deadlock/serialization failure and require retry; and readiness does not represent destination/effect kill switches even though the final provider-I/O transition does. Neither condition can produce a false successful rollback fence or authorize provider I/O after revoked authority: PostgreSQL commits only one side of a deadlock, rollback reports failure unless its full transaction commits, and execute rechecks the destination/effect kill scopes under row locks immediately before its single `reserved -> executing` transition.

## Findings

### F1 — Mixed lock order can make a concurrent rollback require an explicit retry

- **Evidence:** `pec78_mark_composio_slack_effect_executing` locks credential, principal, effect, lease, event, source, capability, destination, and budget in that order (`schemas/cleverwork-roofer/191-pec78-composio-slack-production-hardening.sql:219-266`). Reconciliation locks effect, lease, event, credential, then principal (`:302-310`). Rollback instead locks principal first, then updates source, authorization, gate, capability, destination, budget, credential, lease, event, and finally principal (`:457-488`). A concrete execute/rollback cycle is: execute holds the credential row and waits for the principal; rollback holds the principal and later waits while revoking the credential. PostgreSQL resolves the deadlock by aborting one transaction. If rollback is the victim, execute resumes against the still-active principal/credential tuple and can return `provider_io_authorized=true` (`:279-284`). The retained preview harness labels its checks `authorityRaces`, but each mutation commits before execute and is restored afterward; it never overlaps sessions or asserts rollback wins (`app/command-center/scripts/pec78-db-integration.mjs:186-224,260-275`).
- **Impact:** A rollback attempt racing an already-open execute/reconcile transaction can fail visibly and require operator retry, delaying containment. This is not a bypass of a successful rollback fence: if rollback is aborted it returns no success, while if rollback commits the competing transaction cannot commit through the revoked/fenced rows. An execute transaction that linearizes first represents provider authority granted before rollback took effect, not authority granted after a successful rollback.
- **Fix:** Define one global lock order and use it in every state transition, preferably principal -> credential -> event -> lease -> effect -> source/grant/destination/budget (or a principal-scoped advisory transaction lock acquired first by execute, reconcile, claim/reserve, and rollback). Make rollback retry serialization/deadlock failures within a bounded operator contract, but do not rely on retries as the primary fence. Add real two-connection tests that pause after the first lock and prove rollback cannot lose to execute, no call returns provider authorization after rollback begins/commits, and reconciliation remains available after the fence.
- **Priority:** P2
- **Confidence:** High

### F2 — Readiness does not surface destination/effect kill-switch state

- **Evidence:** The readiness authority tuple joins the active destination grant (`191:372-405`), but `v_no_kill` checks only global, contract, principal, credential, and receive/send capability scopes (`:406-414`). It does not check a `destination` kill targeting the joined destination grant. The SQL then computes `v_ok` from `v_tuple_ready and v_no_kill` and returns `no_kill_switch=true` (`:431-441`). The server trusts those booleans and reports `server_ready` when every check is true (`app/command-center/src/lib/pec78/readiness.server.ts:37-57`). The preview harness tests destination and effect kills only at the execute transition; it does not assert readiness degrades for the destination kill (`pec78-db-integration.mjs:212-224`).
- **Impact:** Operators can receive `server_ready` for the installed database/app tuple while a destination-specific kill will make the activation attempt fail closed at execute. This weakens diagnostic fidelity and can waste the one-event activation window, but it cannot authorize an incorrect send: the final provider-I/O transition locks the exact destination/effect and returns `provider_io_authorized=false` for either kill. External trigger state and other activation evidence are already explicitly outside this server-readiness result.
- **Fix:** Bind the readiness query to the exact destination row and include `k.scope='destination' and k.target=d.id::text` in the no-kill predicate. Treat effect kills as relevant only when an effect exists; readiness already requires no pending/unknown work, so document that distinction. Add preview assertions for every readiness-relevant kill scope, especially destination, and retain the observed degraded result.
- **Priority:** P2
- **Confidence:** High
