## Findings

### F1 — Server readiness does not cross-check the configured trigger or surface destination kills

- **Evidence:** `getComposioProductionReadiness` calls `pec78_composio_production_readiness` with runtime instance, registry, and build, but not `PEC78_COMPOSIO_TRIGGER_ID` (`app/command-center/src/lib/pec78/store.server.ts:172-178`). The database query requires a non-placeholder source trigger and binds the activation authorization to that source trigger (`schemas/cleverwork-roofer/191-pec78-composio-slack-production-hardening.sql:359-405`), while the app separately checks only that its trigger setting is syntactically shaped (`app/command-center/src/lib/pec78/readiness.server.ts:24-45`). The readiness kill predicate covers global, contract, principal, credential, and receive/send capabilities but not the joined destination (`191:406-420`). The final provider-I/O transition does check the exact destination and effect kill scopes immediately before its single `reserved -> executing` update (`191:259-284`). The readiness response explicitly states that Orgo worker and Composio trigger state require separate live operator evidence, and the activation plan requires exact new-trigger identity plus disabled state before trigger-last activation.
- **Impact:** A server-only readiness snapshot can be green while the separately configured trigger differs from the authorized database trigger, or while a destination kill will intentionally deny execution. This can make diagnosis less direct and can waste the one-event activation window if operators ignore the mandatory external evidence gate. It cannot ingest through a mismatched trigger or authorize provider I/O through a destination/effect kill: both operation paths fail closed.
- **Fix:** Version the readiness RPC to accept and compare the exact configured trigger ID (or its reviewed digest) with the joined source and activation rows. Include the joined destination in the readiness kill predicate, document that effect kills are relevant only after an effect exists, and add negative app/PostgreSQL cases for configured-trigger mismatch and destination kill. Continue treating live trigger and worker state as independently collected operator evidence.
- **Priority:** P2
- **Confidence:** High

### F2 — Safe stage bounds do not form one explicit attempt deadline

- **Evidence:** Claim creates a three-minute database lease (`191:182-198`), and the reserved effect expires two minutes after reservation in migration 190. Hermes is bounded to 60 seconds both at the worker call and child-process timer (`deployment/remote/orgo/maya-slack-listener/production-worker.mjs:38`; `hermes-runner.mjs:69-72`). Composio execution receives a 30-second abort signal (`production-worker.mjs:48-53`; `request-options.mjs:1-15`), and the pinned non-idempotent SDK path uses zero retries. Each Command Center token/operation request has its own 30-second timeout (`cc-client.mjs:30-60`). The database checks the lease again immediately before uniquely authorizing provider I/O (`191:235-284`).
- **Impact:** Slow sequential control-plane calls can consume lease headroom after inference and cause a fail-closed quarantine. The current design prevents provider I/O after an expired lease, so this is an availability/latency-budget issue rather than an authorization or duplicate-send issue.
- **Fix:** Carry one monotonic attempt deadline from claim through inference, reservation, execution, provider call, and reconciliation. Require a documented minimum remaining-lease margin before inference and provider execution, retain the database-time check, and add worst-case timing tests.
- **Priority:** P2
- **Confidence:** High
