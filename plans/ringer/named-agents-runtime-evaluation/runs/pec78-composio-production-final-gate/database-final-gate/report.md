Execute re-reads all current authority while holding that lock, and rollback holds it through the complete fence and receipt append. A token issuance racing rollback can therefore deadlock and make one transaction retry. This cannot survive a successfully committed rollback or bypass the final execute fence, but it leaves avoidable containment availability risk and means the advisory-lock discipline is not literally complete across the runtime authorization plane.

## Findings

### F-01 — Token issuance remains outside the rollback serialization lock

- **Evidence:** `public.pec78_authorize_token` selects and locks the credential first and the principal second, without acquiring `pg_advisory_xact_lock(hashtextextended('pec78_maya_runtime_transition',0))` (`schemas/cleverwork-roofer/189-pec78-maya-shadow-boundary.sql:64-91`). Composio rollback acquires that advisory lock, then locks the principal, and later updates credentials (`schemas/cleverwork-roofer/191-pec78-composio-slack-production-hardening.sql:456-489`). A concrete cycle remains possible: token issuance holds the credential and waits for the principal while rollback holds the principal and waits for the credential. By contrast, request authorization, reserve, execute, reconcile, completion, ingress, and claim all acquire the shared advisory lock before row locks (`190:198,340,445`; `191:36,142,224,308,468`). The retained two-session proof exercises rollback versus execute, not rollback versus token issuance (`app/command-center/scripts/pec78-db-integration.mjs:291-315`).
- **Impact:** PostgreSQL can abort either transaction as a deadlock victim. If rollback is aborted, the operator receives a visible failure and must retry while token issuance may complete under the still-unfenced state. This is an availability and containment-latency weakness, not authority after a successful fence: rollback is reported successful only after its all-or-nothing transaction commits, and every Slack provider-I/O attempt must subsequently pass the separately serialized execute RPC's fresh credential, principal, gate, source, grant, destination, budget, lease/fence, and kill checks.
- **Fix:** Replace `pec78_authorize_token` in a forward migration so it acquires `pec78_maya_runtime_transition` before any row lock. Document and use one order for all principal-scoped runtime RPCs. Add a two-connection token-versus-rollback test that deliberately blocks token issuance behind rollback and asserts rollback commits, token issuance fails closed, and no replay/token claim row is retained; retain bounded retry handling for SQLSTATE `40P01`/`40001` as defense in depth.
- **Priority:** P2
- **Confidence:** High

The supplied successful `zmkddrpracgxuuxiyipi` result therefore confirms the exact current files parse/apply from an empty runtime schema, subject to the retained-evidence assumption below.
- Migration 191 revokes `service_role` from the unsafe v1 ingest and zero-argument readiness functions. The v2 ingest and four-argument readiness signatures match the store calls and catalog assertions exactly. Existing service-role grants on claim, reserve, execute, reconcile, and completion persist across `CREATE OR REPLACE`; direct table privileges remain revoked.
- All six Composio production tables are forced-RLS and have no `service_role` direct DML. Receipt append helpers are not executable by `service_role`; public RPCs use fixed `search_path` values and expose only the named definer interfaces.
- V2 ingress serializes on the runtime advisory lock and locks the exact source, principal, active runtime credential, receive grant, migration-191 gate, and one-use validation authorization. It binds runtime, registry, build, trigger, account, user, team, channel, owner, fence, mode, and freshness. Authorization consumption and ciphertext insertion share one transaction, so a failed ciphertext constraint rolls consumption back.
- Concurrent validation ingress is serialized conservatively and admits one fresh event. Delivery and message digests have separate uniqueness constraints, and source/authorization locking prevents two distinct deliveries from consuming the one-event authorization. Concurrent claims share the advisory lock and yield one lease plus one empty result.
- Reserve and execute share the rollback lock. Execute locks and validates credential, principal, effect, lease, event, exact migration/build/registry gate, source, send capability, destination, budget, and global/contract/principal/credential/capability/destination/effect kills before the sole `reserved -> executing` update. An already executing effect is explicitly ambiguous and returns `provider_io_authorized=false`; the route also rejects any replay or response lacking the exact authorization bit.
- Reconciliation holds the shared transition lock and atomically updates effect, event, lease, and two linked receipts. Successful state is `succeeded/completed/completed`; failure/unknown paths terminally quarantine. Claim excludes every event having any effect row, so terminal or ambiguous effects cannot be reclaimed.
- Readiness fails closed as a joined authority tuple. The exact runtime, registry, build, trigger, credential, migration-191 gate, validation source, receive/send grants, Slack destination, budget, and unconsumed activation authorization must coexist and be current. A separate no-kill query includes the exact destination row, and final readiness also requires a healthy receipt link chain, no active lease, no executing/unknown effect, and an empty pending queue.
- The two-session rollback/execute proof is a valid rollback-first serialization test: one reserved connection begins a transaction and holds the advisory lock, a second pool connection starts execute and blocks, the first invokes the re-entrant rollback RPC and commits, and only then can execute continue and observe the fence. This proves no execute authorization can linearize after a rollback that acquired the lock first. If execute acquires the lock first, its committed authorization is correctly ordered before rollback rather than after it.
- Rollback installs the principal kill, revokes source, activation authorization, production gate, both Slack capabilities, destination, budget, and credentials, fences active leases, quarantines pending events, increments the principal fence, and appends a rollback receipt in one transaction. It intentionally retains all effect rows and reports `reconciliation_required` for reserved, executing, or failed-unknown effects. Reconciliation remains callable after authority revocation for executing/unknown evidence because it validates identity/binding but does not require active credential/principal state.
- Event receipts reject update and delete through the inherited trigger, and direct DML is revoked. Receipt appends use their own advisory chain lock. The proof's mutation attempt fails, and rollback evidence remains in the append-only chain together with retained effect rows.
- Package changes are limited to the `pec78:db-integration` script and dev-only `postgres@3.4.7`; the lockfile records version, integrity, license, and engine metadata.
- Focused local results: database harness syntax check passed; PEC-78 Vitest passed 5 files / 45 tests. No Supabase, production, retained preview, Composio, Slack, or other external state was contacted or mutated.
