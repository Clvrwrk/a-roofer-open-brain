## Findings

### F-01 — Activation still depends on a fresh, retained live evidence packet

- **Evidence:** Application readiness deliberately describes itself as `server_ready` and states that Orgo worker and Composio trigger state require separate live operator evidence (`app/command-center/src/lib/pec78/readiness.server.ts`). The activation plan separately requires a matching deployed commit, production migration/preflight and backup proof, exact stopped Supervisor/archive evidence, old and new trigger disabled-state evidence, empty queue/no active lease/no unknown effect, and Christopher's fresh one-event authorization (`plans/ringer/named-agents-runtime-evaluation/PEC78-MAYA-COMPOSIO-PRODUCTION.md`). The database proof harness hard-refuses the production project and records only non-production proof.
- **Impact:** Local tests and retained preview evidence cannot establish that the production build, migrations, environment, Orgo release, Supervisor state, Composio trigger, or destination kill state currently match this candidate. Reusing stale evidence could make an otherwise safe source package operationally unsafe to activate.
- **Fix:** At activation time, retain one timestamped reconciliation packet containing the deployed `buildCommit`, migration and backup proof, registry/runtime/credential tuple, readiness response for the exact new trigger, applicable kill-switch result, exact Supervisor `STOPPED` evidence and release hash, legacy quarantine evidence, old-trigger-disabled and new-trigger-disabled confirmations, empty queue/lease/unknown-effect state, and Christopher's one fresh authorization. Start the worker only after those checks and enable the reviewed new trigger last.
- **Priority:** P2
- **Confidence:** High

### F-02 — Stage limits are fail-closed but do not share one end-to-end attempt deadline

- **Evidence:** The database lease is 180 seconds; Hermes has a 60-second timeout and 4,000-byte output ceiling; Composio send has a 30-second abort timeout and zero retry; and each Command Center token/operation request has its own 30-second timeout (`schemas/cleverwork-roofer/191-pec78-composio-slack-production-hardening.sql`, `deployment/remote/orgo/maya-slack-listener/hermes-runner.mjs`, `request-options.mjs`, and `cc-client.mjs`). The final executing RPC rechecks lease/effect expiry immediately before authorizing Slack provider I/O, but the worker does not carry a single monotonic deadline across inference, reservation, execution, send, and reconciliation.
- **Impact:** Sequential control-plane latency can exhaust lease headroom after inference, producing a fail-closed quarantine and manual reconciliation. The current checks prevent a late or duplicate Slack send, so this is an availability and operator-load risk rather than an authorization bypass.
- **Fix:** Carry one monotonic attempt deadline derived from the claimed lease through every stage, require minimum remaining headroom before inference and provider execution, and add a worst-case timing test. Retain the existing database-time checks and no-retry ambiguity behavior.
- **Priority:** P2
- **Confidence:** High
